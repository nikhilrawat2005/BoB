1. WHAT THIS IS
--------------------------------------------------------------------
Given a website URL, Bob explores it like a real human tester inside a
REAL BROWSER (Playwright), infers what the site claims/should do, then
compares claim vs reality and produces an evidence-based bug report.
Covers: functional bugs, UX/visual issues, cross-page inconsistencies,
false claims (e.g. "AI-powered"), broken flows, network errors.

5. WHY CRAWLER IS NOT A TESTER
--------------------------------------------------------------------
Crawler = fetch HTML + parse with cheerio. Misses:
- real browser DOM + JS execution
- visual/layout defects
- console errors, failed network requests
- interaction bugs (forms, clicks, navigation)
- responsive/mobile issues
Backend-hidden correctness of a site's API calls also needs a real browser
to observe request/response.

--------------------------------------------------------------------
6. THE 6-PHASE PIPELINE
--------------------------------------------------------------------
PHASE 1 - DISCOVERY CRAWL (Playwright)
  - Launch Chromium, visit start URL.
  - Build navigation map: visible + hidden links, sitemap hint.
  - NO fixed page cap (mirror seoService): SAFETY_CAP 10,000 + wall-clock
    deadline (configurable, default ~60s). crawl.truncated flag on deadline.
  - Record per-page: URL, title, internal links, assets.

PHASE 2 - PURPOSE INFERENCE (Gemini)
  - One parallel batch (runParallelGemini).
  - Input: homepage text + discovered page titles + nav structure.
  - Output JSON: { purpose, primaryUserJourneys[], claimedFeatures[],
    explicitClaims[], contentTypes }. Anything the site SAYS it should do.

PHASE 3 - SEQUENTIAL EXPLORATION (browser, ONE page at a time)
  - For each discovered page / journey:
    * happy-path walk + invalid/boundary inputs
    * repeat actions, back/refresh, multiple viewports (desktop/mobile)
  - Capture PER ACTION: screenshot, console messages, network requests/
    responses (status, timing), page timing, accessibility snapshot.
  - Browser is sequential by design (real-testing semantics).

PHASE 4 - BULK TRIAGE (Gemini, parallel)
  - Analyse captured evidence in batches (4 tasks = 2 Gemini + 2 builder
    split, parallel via runParallelGemini / callLLMParallel).
  - Detect: duplicate images, layout/font issues, empty sections,
    broken responsive, dead CTAs, cross-page content/pricing inconsistencies.

PHASE 5 - DEEP CLAIM VERIFICATION (Claude / builder bucket)
  - For each claim from Phase 2, run a controlled experiment.
  - Root-cause + severity + confidence per finding.
  - Buckets: confirmed / likely / UX / capability-verification.

PHASE 6 - REPORT ASSEMBLY
  - Structured finding: { url, action, expected, actual, evidence,
    category, severity, confidence }.
  - HQ card + detailed view + PDF via documentGenerator.generatePdf
    + stored via fileService.

--------------------------------------------------------------------
7. DATA MODEL
--------------------------------------------------------------------
Firestore: users/{userId}/website_tests/{testId}
  testId = generated at start.
Fields:
  { url, status: 'queued'|'running'|'done'|'failed',
    progress: { phase, done, total },
    startedAt, finishedAt,
    site: { title, pageCount, truncated, tookMs },
    purpose: { summary, journeys[], claims[] },
    findings: [ { url, action, expected, actual, evidence,
                  category, severity, confidence } ],
    evidence: { screenshots: [], console: [], network: [] },
    reportPdf: { fileId, url },
    summary, error }

--------------------------------------------------------------------
8. REST API (routes/websiteTester.js)
--------------------------------------------------------------------
POST   /api/website-tester            { url }           -> start (return testId)
GET    /api/website-tester            -> history list
GET    /api/website-tester/:id        -> status + results (live progress)
GET    /api/website-tester/:id/pdf    -> stored report PDF
DELETE /api/website-tester/:id        -> delete test + evidence files
(optional) POST /api/website-tester/:id/rerun

--------------------------------------------------------------------
9. JOB LIFECYCLE
--------------------------------------------------------------------
queued -> running (Phase 1..6, progress updated per phase)
       -> done   (results + PDF stored, summary written)
       -> failed (error message + partial evidence kept)
Simple polling from the frontend: GET /:id every 2-3s.

--------------------------------------------------------------------
10. LLM KEY STRATEGY
--------------------------------------------------------------------
- Parallelism ONLY at LLM level, browser stays sequential.
- Batch = 4 tasks: 2 Gemini keys + 2 builder keys simultaneously.
- Reuse runParallelGemini(tasks, {concurrencyPerKey:2, fallbackFn, model})
  and callLLMParallel with role split.
- Failover automatic: 429/quota -> next key -> OpenRouter fallback.
